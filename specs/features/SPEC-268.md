## 3. 为什么做

站点常静默尝试 `intent://` / 自定义 scheme。巡页在阻止关闭时仍会提示「没有可打开此链接的应用」，并吃掉导航，用户需再点一次。要对齐 Chrome 式静默，并在有 fallback 时自动进 https。

## 4. 本次范围

要实现：

- 阻止关闭：无可用应用 / 打开失败 → 无 snack；有可用应用且用户手势 → 系统选择器。
- 阻止开启：仍 snack「已阻止打开其它应用」，不打开外应用。
- `intent://` 含 `browser_fallback_url` 且未打开选择器（或已阻止）时，自动加载该 http(s) 回退，减少再点。
- 无手势外链：不弹选择器；有 fallback 则跟；否则静默丢。
- 默认 `blockExternalApps=false`（保持）。

明确不做：

- 不改广告拦截、弹窗拦截、点选屏蔽。
- 不为自定义 scheme 发明非标准 fallback。
- 不强制覆盖用户已存「阻止」开关值。
- 本轮不 assemble（除非操作者另要求）。

## 5. 用户如何使用

1. 打开会尝试唤端的网页（阻止关闭）。
2. 无可用应用：无提示；若有 intent fallback，页直接进 https。
3. 有可用应用且为点击触发：弹出系统应用选择器。
4. 开启阻止：见「已阻止打开其它应用」；有 fallback 仍进 https。

## 6. 产品规则

- 当阻止开启且导航为外链时：必须提示「已阻止打开其它应用」；不得启动外应用；若有 http(s) fallback 必须跟进。
- 当阻止关闭、有用户手势、且存在可处理该 Intent 的应用：必须弹系统选择器；不得再 snack「没有可打开…」。
- 当阻止关闭且无可处理应用或打开失败：必须静默；不得 snack；若有 http(s) fallback 必须跟进。
- 当阻止关闭且无用户手势：不得弹选择器；有 fallback 则跟，否则静默。
- 系统不得在阻止关闭时因空 Chooser / 无应用提示打断浏览。

## 7. 重要状态与边界

| 情况 | 用户应该看到什么 | 数据或状态如何处理 |
| --- | --- | --- |
| 关阻止 + 手势 + 有应用 | 系统选择器 | 不跟 fallback（用户可进 App） |
| 关阻止 + 手势 + 无应用 + 有 fallback | 直接打开 https 回退页 | 静默，无 snack |
| 关阻止 + 手势 + 无应用 + 无 fallback | 当前页不变 | 静默消费外链 |
| 关阻止 + 无手势 + 有 fallback | 进 https 回退 | 不弹选择器 |
| 开阻止 + 有 fallback | snack + 进 https 回退 | 不启外应用 |
| 新装机默认 | 阻止开关关 | prefs 默认 false |

## 8. 验收标准

- [ ] AC-01：阻止关闭时，无应用可处理的自定义 scheme / intent 不出现「没有可打开此链接的应用」或「无法打开此链接」snack。
- [ ] AC-02：阻止关闭 + 用户手势 + 有可处理应用时，弹出系统选择器。
- [ ] AC-03：`intent://…S.browser_fallback_url=https%3A%2F%2F…` 在未打开选择器（无应用或无手势）或阻止开启时，主框架加载该 https。
- [ ] AC-04：阻止开启时仍显示「已阻止打开其它应用」，且不启动外应用。
- [ ] AC-05：`blockExternalApps` 默认仍为 `false`；单元测试覆盖 fallback 解析与 `isExternalAppLaunch`。
